## Numbered findings for approval

### 1. HIGH | Keyboard focus can disappear on primary actions
**Rules:** R-32 (keyboard accessibility), R-35 (verify before delivery).
**Evidence:** `assets/styles.css` defines `.button-primary:focus-visible` and `.button-secondary:focus-visible` with `outline: none` near the base button rules; `.project-link:focus-visible` also sets `outline: none`. The generic `:focus-visible` rule is lower-specificity, so it does not reliably restore a visible outline. Project links are already underlined at rest, so underlining on focus is not a distinct focus cue.
**Proposed fix:** Add a consistent, high-contrast focus ring for links, buttons, menu controls, and details summaries. Test keyboard traversal on the homepage, Work, case studies, and mobile navigation.

### 2. HIGH | Latest responsive corrections still lack a completed validation run
**Rules:** R-03 (mobile), R-35 (verify before delivery).
**Evidence:** The earlier mobile WebKit capture visibly clipped the interview-coach preview. PR #24 subsequently changed `assets/editorial.css` to preserve three preview steps, but the newest workflow run 40217703938 was still in progress when checked, and no post-fix mobile screenshot was available.
**Proposed fix:** Obtain a completed desktop/mobile browser run and fresh captures at 390px, 768px, 1280px, and 1600px; verify no clipping or horizontal overflow and that links, menu, and focus work. If the browser-installation step remains blocked, report it as unverified rather than claiming a pass.

### 3. MEDIUM | The mobile homepage delays the first project example
**Rules:** R-14 (cards must serve a purpose), R-05 (content-driven layout).
**Evidence:** In the captured mobile homepage, the four-row Career File and five-item impact strip precede the first featured case. Visitors seeking proof of work must scroll through substantial repeated profile information before reaching an example.
**Proposed fix:** Test a mobile-only progressive disclosure or tighter arrangement of the Career File, while preserving every evidence link and the scope figures. Do not remove claims or alter desktop hierarchy without a visual comparison.

### 4. MEDIUM | A working application has a text-only cover in the Work grid
**Rules:** R-22 (illustrations should communicate the subject), R-14 (card purpose).
**Evidence:** `work.html` uses a typographic `file-cover` for SOMA Budget Planner, while its card separately links to a working browser application. The captured desktop grid therefore shows a title/list where a genuine product view could demonstrate the software more directly.
**Proposed fix:** With owner approval for the asset, replace or supplement the cover with a real, appropriately cropped screenshot from the public application. Keep a clear label for the actual app and do not fabricate UI.

### 5. LOW | Several introductory sections repeat the same broad category words
**Rules:** R-16 (specific copy over buzzwords), C-3 (content-driven composition).
**Evidence:** `index.html` repeats “business systems”, “implementation”, and “applied AI” across the hero, featured-work heading, and operating-approach heading. `work.html` opens with another general category statement before the cases.
**Proposed fix:** Reduce repetition by making one introductory sentence more specific to the actions shown in the cases, while preserving the user's approved career positioning and factual scope.

### 6. MEDIUM | The mobile interview-coach preview uses very small text
**Rules:** R-06 (readable typography), R-03 (responsive).
**Evidence:** The corrective mobile CSS in `assets/editorial.css` uses `.6rem` for the preview header and `.65rem` for step descriptions, while keeping three columns at narrow widths. The illustration is correctly marked decorative, but the miniature labels may be visually hard to read.
**Proposed fix:** Evaluate the final mobile capture before changing it. Prefer fewer readable labels or a simplified illustrative layout to shrinking the text further.
